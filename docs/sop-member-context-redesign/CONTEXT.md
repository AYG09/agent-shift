# SOP 구성원 업무맥락 흐름 재설계 컨텍스트

## 1. 분석 단위와 목적

- 분석 단위: 구성원이 Task 기반 SOP 생성을 시작해 편집 가능한 Task–Activity–Skill Work Map을 확정하기까지의 사용자 여정
- 목적: 구성원이 업무맥락을 먼저 제공하고, AI 추천과 사람의 확인을 거쳐 자신의 업무 구조를 검토·수정하게 만드는 저혼란 데스크톱 경험
- 후속 연결: 확정 Work Map과 동일한 업무맥락은 기존 Task-wide Activity–Sub Action SOP 생성의 입력이 된다.

이 사안에는 행동경제학의 **인지 부하와 점진적 공개** 관점이 유의미하다. 한 화면에 모든 선택지를 노출하는 대신 한 단계당 하나의 주된 결정을 요구하면 사용자가 현재 해야 할 행동과 결과의 원인을 더 쉽게 이해할 수 있기 때문이다.

## 2. 검증된 사실과 근거

### 2.1 최신 고객 요구

1. 구성원 정보 입력과 로그인 게이트가 먼저 존재해야 한다.
2. 로그인된 구성원이 현재 수행 중인 업무 내용과 맥락을 별도 페이지에서 작성해야 한다.
3. 업무맥락 입력 페이지에는 `확인` 또는 `입력 완료` 성격의 명시적 제출 액션이 있어야 한다.
4. 제출 후 AI는 구성원이 입력한 업무맥락을 기준으로 Task Library DB의 Task 중 의미적으로 가장 관련성이 높은 Task를 추천해야 한다.
5. AI 처리 중에는 로딩만 보여주지 않고, 프로그램의 목적과 다음 행동을 설명하는 도움말을 반복·순환해서 제공해야 한다.
6. Task가 추천되면 해당 Task의 Activity와 Skill을 표로 보여줘야 한다.
7. 구성원은 Task, Activity, Skill을 자신의 실제 업무패턴에 맞게 수정할 수 있어야 한다.
8. 화면 밀도를 비교하기 위해 간소화 버전과 상세 버전의 두 페이지가 모두 필요하다.
9. 간소화 버전은 T/A/S의 핵심 정의를 중심으로, 상세 버전은 세부 설명까지 보여줘야 한다.
10. UI/UX는 `Simple is the best` 원칙에 맞춰 재설계하고 Claude의 디자인 검토 기능을 실제로 사용해야 한다.
11. AI가 생성하는 SOP node는 행동 중심, 능동태, 명확한 판단기준, 평이한 언어, 최소 유효 단일 행동 원칙을 따라야 한다.
12. 개인 SOP 생성과 HR 대표 표준안 생성 모두에 Mission, tool 허용·금지, escalation/HITL 의미가 반영될 수 있어야 한다.

### 2.2 기존 고객 계약 중 계속 유효한 사실

- Task 추천에는 구성원의 조직·직무 맥락도 사용할 수 있다.
- 추천은 자동 선택이나 자동 확정이 아니다. 구성원이 Task를 명시적으로 선택한다.
- 추천 실패 시 수동 Task 검색·선택 경로가 계속 사용 가능해야 한다.
- Work Map에서 Task, Activity, Skill을 추가·삭제·수정하고 Activity 순서를 조정할 수 있다.
- Task-wide 생성은 확정된 모든 Activity를 원본 순서로 포함한다.
- Activity별 Skill 관계를 보존하며, 반복 Skill 관계를 전역에서 평탄화하지 않는다.
- 생산 인증, 생산 DB, 감사 이력, 모바일은 현재 프로토타입 범위가 아니다.
- `/flow`와 해당 컴포넌트는 이 작업에서 변경하지 않는다.

### 2.3 현행 코드 기준선

| 영역 | 현재 구현 | 판단 |
|---|---|---|
| 구성원 진입 | `/sop`의 `SopMemberHome`이 기본 정보·현황·생성 경로를 한 화면에 표시 | 로그인 게이트가 아님. 인증 전/후 상태가 없음 |
| Task 기반 진입 | `/sop/setup`의 `SopSetupGate` | 구성원 정보, 추천, T/A/S, 업무맥락, 생성 설정이 혼재 |
| 업무맥락 | Store의 `context`; Setup 우측 textarea | Task 추천보다 뒤에 배치되어 고객 기대 순서와 다름 |
| 추천 입력 | Store의 `taskRecommendationInput` | SOP 생성 `context`와 별도여서 의미가 어긋날 수 있음 |
| AI 추천 UI | `SopTaskRecommendationPanel`; 기본 접힘인 선택 기능 | 최신 흐름에서는 선택 기능이 아니라 필수 선행 단계 |
| 추천 API | `POST /api/sop/task-recommendations` | 최대 3개 고유 Task ID, 순위·이유, 카탈로그 검증, confidence 없음 |
| T/A/S 편집 | `WorkLibrarySelector` | 기능은 존재하지만 단일 고밀도 편집기이며 두 밀도 비교가 불가능 |
| Task Library 상태 | `WorkLibrarySelection.taskCatalog` 안에서 선택·편집 | 추천 원본 카탈로그와 구성원 편집 스냅샷의 책임이 분명하지 않음 |
| 생성 연결 | `runSopSetupGeneration`과 기존 Activity–Sub Action 계약 | 재사용 대상. 새 진입 흐름 뒤에 연결해야 함 |
| 개인 SOP node 생성 | `getSopPrompt`가 대상+행동동사, 입력/산출물 분리, Activity당 2~3개 분해를 일부 요구 | 책임주체·완료기준·구조화 tool policy·HITL 계약은 미완성 |
| 대표 표준안 | `getStandardDraftPrompt`와 `generateStandardDraftDocument`가 승인 same-Task SOP를 종합 | source summary가 title/definition만 전달해 역할·조건·도구·주의가 유실됨 |

## 3. 현재 문제 정의

### 3.1 정보 구조 문제

- 사용자가 업무맥락을 작성하기 전에 Task Library 편집기를 마주한다.
- 필수 사용자 여정인 추천이 접힌 `선택 기능`으로 표현된다.
- 한 화면에서 구성원 확인, 추천, 데이터 편집, 업무맥락, 모델 설정, 생성까지 동시에 요구한다.
- 현재 단계와 완료 조건이 페이지의 번호나 카드 수로만 드러나며, 실제 상태 전이와 일치하지 않는다.

### 3.2 데이터 일관성 문제

- 추천 입력과 생성 맥락이 두 문자열로 분리되어 AI가 추천한 근거와 SOP 생성 근거가 달라질 수 있다.
- Task Library의 읽기 전용 원본과 구성원이 수정하는 Work Map 스냅샷의 경계가 약하다.
- 추천 결과를 받은 이후 업무맥락이 바뀌었을 때 결과를 유지할지 무효화할지 명시적 규칙이 없다.

### 3.3 밀도 문제

- 대표 Task는 Activity 14개, Activity당 Skill 5개여서 관계 행이 70개에 이른다.
- 현재 편집기는 Task 목록, Task 정의, Activity 목록, Activity 상세, Skill 편집을 한 카드 안에 중첩한다.
- 간소화·상세 버전의 차이가 도메인 데이터가 아니라 화면 투영 방식이어야 하지만 현재는 비교 가능한 별도 뷰가 없다.

## 4. 목표 사용자 여정

```text
[비로그인]
  /sop/login
  구성원 정보 입력
        │ 로그인하고 업무 작성 시작
        ▼
[로그인됨]
  /sop/context
  현재 수행 업무와 맥락 작성
        │ 입력 완료
        ▼
[AI 처리]
  도움말 순환 + 취소 가능 + 가짜 진행률 없음
        │ 성공                         │ 실패
        ▼                              ├─ 입력 유지 후 재시도
  추천 후보 확인                       └─ 수동 Task 검색
        │ Task 명시적 확인
        ▼
[Work Map]
  /sop/work-map/simple  ⇄  /sop/work-map/detailed
  동일한 편집 스냅샷을 서로 다른 밀도로 검토·수정
        │ 검토 완료
        ▼
  기존 Task-wide SOP 생성 → /sop/workspace
```

로그인 완료 후에는 최신 고객 여정에 맞춰 `/sop/context`로 이동한다. 기존 `/sop` 구성원 Home의 SOP 현황, 다른 생성 경로, 승인 추적은 삭제하지 않고 인증된 구성원의 Home으로 보존한다. `/sop` 진입 시 비로그인 상태면 `/sop/login`으로, 로그인 상태면 기존 Home으로 연결한다. 비로그인 사용자가 업무맥락이나 Work Map에 직접 진입하는 것은 금지한다.

## 5. 용어와 권위 원본

| 용어 | 정의 | 권위 원본 |
|---|---|---|
| 프로토타입 로그인 | 구성원 정보를 로컬 세션 맥락으로 설정하는 데모 게이트. 실제 신원 인증이 아님 | member session state |
| 업무맥락 | 구성원이 현재 수행하는 업무, 순서, 예외, 승인, 도구, 협업을 설명한 단일 원문 | `context` 계열 단일 필드 |
| Task 추천 | Task Library 후보를 업무맥락과 직무 맥락으로 순위화한 AI 제안 | 추천 응답; 확정 권위 없음 |
| Task Library | 고객사가 제공하는 Task–Activity–Skill 원본 카탈로그 | fixture/향후 DB adapter |
| Work Map 초안 | 구성원이 선택한 Task를 복제해 자신의 업무에 맞게 편집하는 스냅샷 | member-owned draft |
| 간소화 뷰 | 핵심 명칭과 한 줄 원문을 우선 표시하는 저밀도 투영 | Work Map 초안의 projection |
| 상세 뷰 | Activity·Skill 설명 원문까지 펼쳐 검토하는 고정보량 투영 | 동일 Work Map 초안의 projection |

## 6. 구현 해석

다음은 최신 요구를 현재 프로토타입에서 실행 가능하게 만드는 해석이다.

1. **프로토타입 로그인 필드**: 사번, 이름, 조직, 주요 직무는 필수로 받고 직급은 선택으로 둔다. 이는 생산 인증 정책이 아니라 추천과 화면 시연에 필요한 최소 입력이다.
2. **추천 후보 수**: 기존 검증 계약을 유지해 최대 3개를 반환한다. 1순위를 가장 관련성 높은 추천으로 강조하되 자동 적용하지 않는다.
3. **두 밀도 페이지의 데이터**: 두 페이지가 별도 복제 데이터를 가지지 않는다. 같은 Work Map 초안을 읽고 같은 domain mutation을 호출한다.
4. **정의와 세부 설명의 시제품 표현**: 현행 Task Library에는 별도 `shortDefinition`과 `detailedDescription` 쌍이 없다. 간소화는 기존 `description` 원문을 한 줄로 제한해 보여주고, 상세는 동일 원문 전체를 보여준다. 고객 DB가 실제로 두 필드를 제공하기 전 새 의미 필드를 만들지 않는다.
5. **Work Map 편집**: 간소화에서도 모든 편집 기능은 접근 가능해야 한다. 화면에는 최소 정보만 두고 편집 drawer/dialog에서 전체 필드를 수정한다.
6. **로딩 도움말**: 정적이고 검토 가능한 콘텐츠를 순환한다. 처리율을 알 수 없으므로 숫자형 진행률이나 예상 완료 시간을 만들지 않는다.
7. **고급 생성 설정**: 기존 설정은 기본값으로 유지하고 핵심 흐름에서는 접힌 고급 설정으로 후퇴시킨다. 설정 제거는 이번 요구가 아니다.
8. **AOP 표현**: AOP를 보편 국제표준이라고 주장하지 않고, 이 프로젝트에서는 `agent-ready SOP 작성 계약`의 실무 명칭으로만 사용한다. 실제 agent 실행 권한은 prompt가 아니라 별도 tool executor와 HITL이 강제해야 한다.

## 7. 보류·확인 필요 항목

- 생산 인증 방식, SSO/HR master 연동, 세션 만료와 보안 정책
- 직급과 주요 직무의 실제 출처
- Task 추천의 전사 전체 검색 여부와 Job 범위 우선 검색 여부
- 대규모 Task Library에서 임베딩/벡터 검색이 필요한 시점과 인프라
- Task·Activity·Skill에 `정의`와 `세부 설명`이 각각 별도 DB 필드로 제공되는지 여부
- 구성원이 수정한 Work Map을 조직 Task Library에 반영할지, 개인 SOP 스냅샷으로만 둘지 여부
- 추천 품질 정답 데이터셋, 품질 임계값, 평가 운영자
- 간소화·상세 중 어느 버전을 최종 기본값으로 채택할지
- 실제 tool registry, 직무별 허용 권한, 고영향 행동 분류와 HITL 담당자
- 대표 표준안의 상충 기준·도구 정책을 최종 확정할 역할
- AOP를 대외 제품 용어로 채택할지 여부

이 항목은 프로토타입에 필요한 최소 가역적 동작을 제외하고 임의로 확정하지 않는다.

## 8. 제외 범위

- 승인자·SME·HR 화면의 재설계
- Activity–Sub Action 의미 계약 변경
- Agent화 판단 체계 변경
- 생산 DB, 벡터 DB, 실제 계정 인증, 감사 로그
- Task Library 원본 데이터 정제 또는 스키마 확장
- 동료/과거 SOP 생성 경로의 기능 변경
- `/flow` 코드와 동작
- 모바일·다국어 지원

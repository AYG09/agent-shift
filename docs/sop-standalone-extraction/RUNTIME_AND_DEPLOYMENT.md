# 사내 서버망 런타임·배포 계약

## 1. 목적과 경계

이 문서는 분리된 SOP 앱이 **사내 서버망에서 동작하기 위해 만족해야 할 계약**을 정의한다.
구체 인프라(서버 사양, 오케스트레이션, DB 제품)는 확정되지 않았으므로, **환경이 무엇이든
성립해야 하는 조건**과 **환경이 정해지면 채워야 할 빈칸**을 구분해 적는다.

빈칸을 임의의 값으로 채우지 않는다. 채우는 순간 그것이 "확정 요구"처럼 굳는다.

## 2. 현재 상태에서 바꿔야 하는 것

| 지점 | 현재 | 사내망 요구 | 상태 |
|---|---|---|---|
| AI 키 | 브라우저 `localStorage` BYOK | 서버측 관리 | `AI_PROVIDER_CONTRACT.md` |
| AI 호출 주체 | 브라우저가 트리거, 서버가 외부 API 직통 | 서버가 사내 엔드포인트 호출 | 같은 문서 |
| 저장 | in-memory (재시작 시 소실) | 영속 저장소 | §4 |
| 배포 | Vercel + GitHub 연동 | 사내 배포 수단 | §5 |
| 데모 시드 | `SOP_SCENARIO_SEED_MODE` 기본 활성 | 운영에서는 비활성 | §3 |
| 외부 통신 | Google API 직통 | 외부망 차단 가능 | §6 |

## 3. 환경변수 계약

`REQ-RUN-001`: 앱은 **환경변수 없이도 기동에 성공**해야 한다. 없으면 그 기능만 명확한 오류로
비활성화되고, 프로세스가 죽지 않는다. 현재 `model-factory.ts`가 키 부재를 이미 그렇게
다루므로 이 성질을 유지한다.

현재 존재하는 것:

| 변수 | 용도 | 사내망에서 |
|---|---|---|
| `GOOGLE_GENERATIVE_AI_API_KEY` | provider 키 | provider 교체와 함께 이름·의미가 바뀐다 |
| `SOP_SCENARIO_SEED_MODE` | `disabled`가 아니면 데모 레코드 시드 | **운영에서는 `disabled` 필수** |
| `NEXT_PUBLIC_LIVEBLOCKS_PUBLIC_KEY` | `/flow` 협업 | **이관 대상 아님** — 제거 |

`REQ-RUN-002`: `NEXT_PUBLIC_` 접두사 변수에 비밀값을 넣지 않는다. 이 접두사는 클라이언트
번들에 그대로 들어간다. 새 저장소에는 현재 이 접두사를 쓰는 변수가 남지 않는다.

`REQ-RUN-003`: 운영 기동 시 `SOP_SCENARIO_SEED_MODE`가 `disabled`가 아니면 **기동 로그에
경고를 남긴다.** 데모 레코드가 운영 HR 집계에 섞이는 것이 이 앱에서 가장 조용히 위험한
사고다.

빈칸(환경 확정 후 채움): 로그 레벨, 프록시 설정, 타임아웃, TLS 인증서 경로, 헬스체크 경로.

## 4. 영속성 계약

### 4.1 현재 포트

`SopRepository`(`src/lib/sop-repository.ts`)가 이미 인터페이스로 존재하고,
`sop-repository-memory.ts`가 그 참조 구현이다. 분리 자체는 이 구조를 바꾸지 않는다.

`REQ-RUN-004`: 이관 시 in-memory 구현을 그대로 옮긴다. **분리와 DB 도입을 동시에 하지
않는다.** 두 변경을 겹치면 실패 원인을 가릴 수 없다.

`REQ-RUN-005`: 비영속 상태가 화면에 계속 표시되어야 한다. 현재 구성원 Home이 "서버는
in-memory reference 저장소 기준이며 재시작 시 초기화될 수 있습니다"를 노출한다 — 이 문구를
DB 도입 전까지 유지한다.

### 4.2 실제 저장소 도입 시 지켜야 할 것

`REQ-RUN-006`: 새 구현은 `SopRepository` 포트만 구현한다. 도메인·화면 코드가 DB를 직접 알지
않는다. 이 경계가 깨지면 사내 DB 정책이 바뀔 때마다 도메인이 함께 흔들린다.

`REQ-RUN-007`: 다음 불변식은 저장소 구현과 무관하게 유지된다.

- 구성원은 자기 문서만 편집·제출할 수 있다
- 구성원이 `sme-review`·`approved`·`rejected`를 직접 만들 수 없다
- 승인 단계 전이는 공용 전이 함수만 수행한다
- 반려는 사유 코드와 자유 서술을 함께 요구한다
- HR 집계는 저장된 레코드에서 계산한다 — 화면용 임의 수치를 만들지 않는다

`TST-RUN-001`: 저장소 구현을 바꿔도 위 불변식 테스트가 그대로 통과한다. 현재 테스트가
in-memory 어댑터를 주입해 검증하므로, 새 구현도 같은 테스트를 통과해야 한다.

빈칸: DB 제품, 스키마, 마이그레이션 도구, 백업·보존 기간, 동시성 정책.

## 5. 빌드와 배포 계약

`REQ-RUN-008`: 빌드는 **네트워크 없이 재현 가능**해야 한다. 사내망은 npm registry 접근이
통제될 수 있으므로 lockfile 기반 설치(`npm ci`)와 사내 미러 사용을 전제한다.

`REQ-RUN-009`: 산출물은 자체 호스팅 가능한 Next.js 앱이어야 한다. 현재 코드에 Vercel 런타임
전용 API 의존은 없다 — 배포 수단만 Vercel이었다. 이 성질을 유지한다(플랫폼 전용 기능을 새로
도입하지 않는다).

`REQ-RUN-010`: 빌드 검증은 **Turbopack과 webpack 양쪽**에서 통과해야 한다. 이 저장소에서
`api/ai/route.ts`의 비-route export가 Turbopack은 통과하고 webpack은 실패하는 사례가 실제로
있었다. 한 경로만 확인하면 그런 결함을 놓친다.

빈칸: 컨테이너 이미지 베이스, 오케스트레이션, 리버스 프록시, 무중단 배포 방식, CI 수단.

## 6. 네트워크 경계

`REQ-RUN-011`: 앱이 여는 외부 연결은 **AI provider 엔드포인트 하나**여야 한다. 현재 SOP는
liveblocks·외부 폰트·원격 이미지를 쓰지 않으므로 이 조건이 이미 성립한다. 이관 과정에서
새 외부 의존을 추가하지 않는다.

`TST-RUN-002`: 외부망을 차단한 상태에서 앱을 기동해 다음이 성립하는지 확인한다.

- 모든 화면이 렌더된다 (AI 기능 제외)
- 로그인·업무맥락·수동 Task 선택·Work Map 편집·승인·HR 조회가 동작한다
- AI 호출만 명확한 오류로 실패하고, 입력이 보존되며, 수동 경로가 살아 있다

이 조건은 이미 프로덕션에서 부분적으로 관측됐다 — API 키가 없는 상태에서 추천이 실패해도
수동 검색으로 Work Map까지 도달했다(`W4_BASELINE_A11Y_EVIDENCE.md`).

`REQ-RUN-012`: 외부 폰트·CDN·원격 이미지를 도입하지 않는다. 차단 환경에서 화면이 조용히
깨진다.

## 7. 관측과 진단

`REQ-RUN-013`: AI 호출 실패는 **사용자에게 보이는 오류**와 **서버 로그** 양쪽에 남는다.
사용자 문구는 복구 경로를 포함해야 한다(현재 "Task는 직접 검색해 선택할 수 있습니다"가 그
역할을 한다).

`REQ-RUN-014`: 로그에 개인정보와 자격증명을 남기지 않는다. 특히 업무맥락 원문과 SOP 본문은
개인 업무 내용이므로 전문을 로그로 남기지 않는다.

빈칸: 로그 수집 방식, 보존 기간, 지표 수집, 알림 채널.

## 8. 이관 시점의 운영 기본값

`INT-RUN-001`: 사내망 1차 기동의 기본값을 다음으로 제안한다. 확정값이 아니라 가장 작은
가역적 선택이다.

| 설정 | 1차 기본값 | 이유 |
|---|---|---|
| 저장소 | in-memory | DB 도입은 별도 작업. 비영속 표시 유지 |
| AI | 비활성(키 없음) | 사내 엔드포인트 확정 전까지 수동 경로만으로 전체 흐름 시연 가능 |
| 데모 시드 | `disabled` | 운영 데이터 오염 방지 |
| BYOK UI | 숨김(코드는 유지) | 개인 외부 키 사용을 기본 경로로 만들지 않는다 |

이 기본값으로도 구성원 흐름·승인·HR 조회가 동작한다. AI 연결은 그 위에 얹는 순서다.
